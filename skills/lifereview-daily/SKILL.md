## 数据源

### HAE JSON（`HealthAutoExport-YYYY-MM-DD.json`）
两个目录都检查：`iCloud for Proma/`（主要）、`新自动化流程/`（备用）

### 连续血糖监测（CGM）逐点数据
优先读取 `AutoSync/HealthMetrics/blood_glucose/YYYYMMDD.hae`，不要只依赖 HAE JSON 的日级 `blood_glucose` 字段（iCloud evict 时会缺失）。每个点可能同时有 mmol/L 和 mg/dL 两份记录，必须按时间戳去重并统一为 mmol/L；LZFSE 从文件开头解压。

### 聚合规则 ⚠️
| 方式 | 指标 |
|------|------|
| **sum()** | steps, active_energy, distance, flights, exercise_time, stand_hour, daylight_min |
| **median()** | rhr, respiratory_rate, heart_rate, blood_o2 |
| **mean()** | hrv（v9.1 从中位数改为均值，V 型分布时更诚实）, walking_hr |
| **first** | sleep_analysis, vo2_max |

> 曾因取首个条目而非 sum() 导致步数被低估 100 倍。接入新指标先确认聚合方式。

### 碎步指数（v6，参考 JeffenCheung/personal-health-dashboard）
连续活跃小时合并为 bout。短 bout=单小时<500步，长 bout=≥2h 或 ≥2000步。
碎步指数 0-100 = 短bout比(40%) + 频率(30%) + 平均时长倒数(30%)。A-E 等级：A=持续型 → E=高碎片型。

### 步态指标（v6 新增）
`walk_speed`(3.5-5.5 km/h)、`walk_step_len`(55-75 cm)、`walk_asymmetry`(<3%)、`walk_double_support`(20-30%)

### 跑步步态（周报用）
`running_stride_length`、`running_ground_contact_time`、`running_power`、`running_vertical_oscillation`（仅跑步日有数据）

### 训练记录与恢复观察（2026-07-22）

- 原始训练记录路径：`AutoSync/Workouts/*.hae`。`~/.life-log/tmp/recovery-insights.py` 会把可读记录按 workout id 幂等写入 SQLite `workouts` 表。
- iCloud 占位文件带 macOS `SF_DATALESS` 标志，必须跳过并标注“训练证据不足”；禁止因读取旧训练文件卡住晨报，也禁止把 Looki 的“锻炼/健身”片段替代为正式训练负荷。
- 睡眠储备：用近 30 次个人睡眠中位数作参照，至少 14 次历史和连续 3 晚数据才展示。它描述累计睡眠差，不把单晚短睡自动说成睡眠债。
- 恢复延续性：只以连续日 HRV 的 lag-1 相关做预测背景，至少 14 对数据；不得写成生理因果。训练后多日恢复曲线至少需要 10 次个人高负荷事件与后续复现，前期只写“观察中”。

### Looki API — 两条独立管道
🔵 Moments（AI 处理，数小时延迟）/ 🟢 Realtime（即时）。先 realtime 后 moments。VPN 用 Python 直连 IP 绕过。
详见 `references/looki-protocol.md`

### 飞书日历（仅已接受）
三层漏斗：① accept ② 自己是组织者 ③ 航班/高铁/→箭头。排除系统日程和提醒型。
API 失败时保留已有数据，不覆盖。

**日历解读铁律（2026-07-05）**：
- 你的日历不只有会议——还包括训练、打扫、吃饭、出行、购物等个人生活安排
- **日历空白 ≠ 空日子**。周末可能有深度工作块，工作日可能有全天外出
- 个人备注型日程（"砍重量""写材料""准备""打扫"）是合法日程，不是冗余
- **accepted < 2 条时禁止写"零场会"**。改为"周日，今日日程较轻松"，并主动拉 Looki 补充

## 评分逻辑

- **精力+压力**：Looki ≥5 moments→权重0.8，3-4→0.6，<3→0.3；Looki离线用日历+生理替代
- **专注（晨间预判）**：睡眠+HRV+RHR+呼吸+昨日🆘🍬级联
- **awake_to_work_gap**：每日必须计算（首个工作 moment − 起床时间），<10min=高应激、10-30min=正常、>30min=良好缓冲，纳入精力评估
- **RHR 偏离诊断**：分析 RHR 偏离时必须对照已验证因果规律库给出最匹配解释（酒精/出行/睡眠剥夺/运动恢复等），不能只说"升高了"
- **状态信号**：🆘求救（刷手机/发呆）、🍬代偿（可乐/零食/咖啡）、😴恢复（小憩/午睡）。Looki 无可用数据时**必须显式标注**「Looki 无数据，信号无法提取」，不能沉默跳过
- **CGM 状态对应**：只在当日 CGM 覆盖 ≥20h 且 RHR、HRV、睡眠齐全时，才判断血糖形态与恢复状态是否同步；关键恢复数据缺失时，只报血糖事实并明确「不做血糖-状态对应」。

## CGM 血糖 × 行为 × 状态规则（v4.9 · 2026-07-31 三级覆盖分层）

1. **先做数据审计**：显示样本数、覆盖时长、日均、范围、CV、3.9-7.8 区间占比、清晨 04:00-08:00 均值。cgm-extract.py 自动输出 `coverage_tier`（full/partial/fragment）、`sensor_status`（active/outage/recovering）、`outage_days`、`recovery_day`。
2. **三级覆盖分层**（替代旧 <20h 一刀切）：
   - **full（≥20h）**：全量分析（TIR + CV + 餐次 + 状态对应）
   - **partial（4-20h 且 ≥48 点）**：覆盖段内的局部形态分析（逐小时趋势、应激 spike 检测、已覆盖段餐次窗口血糖响应），标注「覆盖不完整，不做全天状态对应」
   - **fragment（<4h 或 <48 点）**：仅报血糖事实，不做关联
3. **断采/回归感知**：`sensor_status=recovering` 时标注「CGM 断采 N 天后回归首日，传感器校准期开局读数可能偏高」；`sensor_status=outage` 时标注「CGM 断采中，已断 N 天」。
4. **餐次标签优先级**：① Looki 明确标题（早餐/午餐/晚餐/外卖/食堂/餐厅/咖啡/奶茶/零食）→ ② `glucose-meals.py` 的 `infer_meal_windows()` 推断餐次（标注 confidence=low，步数↓25%+血糖↑0.3）→ ③ 无餐次标签时只报血糖曲线和应激 spike。推断餐次不得用于结论性餐后响应评级，仅作观察参考。
5. **餐后用稳指标**：餐前 30min 中位数、餐后 0-150min 峰值及峰值时点、100-140min 平均值（约 2h）。不以单次 `峰值-餐前` 排名或下结论，餐前基线不同会制造假差异。
6. **行为对应**：只记录餐后 120min 内明确标注的步行/骑行/跑步/训练等活动；餐前 45min 内若有明确会议/工作场景且曲线在餐前 10min 上行 ≥0.5 mmol/L，可写「与高负荷场景同窗，仅作观察」，禁止判定为应激性高血糖。
7. **状态对应**：仅 coverage_tier=full 时执行。以近 14 日（至少 5 天）CGM 日均中位数为背景。若 CGM 平稳（TIR≥95%、CV≤15%）而 RHR/HRV/睡眠偏离，写「不同步，不能把恢复偏离归因于血糖波动」；若同日都偏离，只写「同向变化，累计多日再验证」。
8. **边界**：CGM 在此系统中用于 n-of-1 行为观察，不用于医学诊断、疾病筛查或给出用药/饮食治疗建议。

## 已验证因果规律

> 📌 **完整清单（含观察级/待验证项）** → `.claude/memory/lifereview.md`「已验证的因果规律」段（12 条）。以下为日常分析直接引用的核心规律（9 条），其余 3 条（会议密度不决定精力 / 同床深睡 / 运动时间）在对应分析维度中按需引用。

- 🔴 酒精 → RHR +5~+6 bpm（最强预测器，基因层面确认慢代谢型——自行做基因检测验证）
- 🔴 深睡翻倍 ≠ 睡得好（白天透支的维修账单）
- 🟡 代偿日精力低 ~0.7（不是意志力，是生理信号）
- 🟡 运动日精力反而更低（恢复没跟上）
- 🟡 代谢综合征风险（内脏脂肪 + 血管指标，腰臀比/CT 自查）
- 🟡 出行日 ≈ 酒精日的生理代价（航班/高铁+日程密度+睡眠剥夺 → RHR +5~+6，与酒精同级的高交感负荷）
- 🟡 入睡晚是"睡得晚"不是"睡不着"（2026-07-18 Looki 印证）：入睡≥1:00 的日子，睡前 2-3h 都有高强度脑力活动（技术研讨会/播客录制/行车办公/差旅夜航）。入睡时间 vs 睡眠时长 r=-0.62（晚睡直接吃时长），但 vs HRV r=0.03（不直接拉低质量）。主因是睡前大脑激活，日照不足是相位叠加因素
- 🟡 咖啡/茶饮不影响 HRV（观察级，待更多样本）：7 天对比无显著下降，与酒精形成对比
- 🟡 HRV 夜间分布形态比均值更准：前半夜低后半夜飙升的 V 型 = 副交感过度补偿/紧急修复，均值看似恢复实际未恢复

## 观察规则：日照×入睡晚（20260718, #42）

**触发条件**（晨报自动检查，满足≥2 条即提醒用户）：
1. 当日 `daylight_min` < 20（日照严重不足，历史 P25 以下）
2. 当晚 `sleep_start` ≥ 01:00（入睡晚，P75 以上）
3. Looki moments 显示 22:00 后仍有工作/会议/录制场景（睡前高强度脑力）

**提醒话术**：
- 日照低 + 入睡晚：「☀️ 昨日日照仅 Xmin（P-Y），当晚入睡 X:XX。日照不足推迟昼夜相位，建议今天上午出门走 15 分钟补晨光」
- 叠加睡前脑力活动：「⚠️ 22 点后仍在 [技术讨论/播客录制/行车办公]，大脑激活推迟入睡。建议今晚 23 点前停止高强度脑力」

**数据来源**：
- `daylight_min`：canonical.daylight_min（health-extract.py v10+ 从 HAE `time_in_daylight` 提取）
- `sleep_start`：canonical.sleep_start
- 睡前活动：Looki moments 22:00-02:00 段

**分析脚本**：`~/.life-log/tmp/daylight-analysis.py YYYY-MM-DD`（单日）或无参数（多日关联）

**当前局限**：HAE 只导出日照日总量，无晨光时段（6-10 点）分布。晨光时段需后续从 Apple Health 原始 XML 补。n=38 已确认证伪（r=0.17，2026-07-29 复看）。

## HRV 数据口径（v4.5 · 2026-07-02 事故教训）

**事故**：某异地夜 HRV 5 次采样呈 V 型（示例 [70, 40, 40, 40, 70]），中位数=40。报告说「HRV 暴跌，系统透支」。实际早晨已恢复至 71，用户主观感受「非常好」。中位数 42 把 V 型恢复曲线压成了一个灾难数字。

**规则**：

1. **主报 7 日滚动均值，不报单夜中位数**。`hrv_7d_avg` 才是稳定信号。单夜中位数只作为补充参考
2. **HRV 数字必须带口径**：样本数（hrv_n）、范围（hrv_range）、早晨恢复读数（hrv_morning）。格式：`7 晚均值 56ms（4 晚），昨晚中位数 42ms（5 次采样，范围 40-71，晨间已恢复至 71）`
3. **<3 次夜间采样时强制标注「小样本」**（hrv_sparse=true，Apple Watch 夜间正常 4-6 次，<3 才算稀疏。health-extract.py 20260705 修正，原阈值 5 太激进）
4. **HRV 单夜值聚合方式**：取 0-9 点所有读数的**均值**（v9.1 从中位数改为均值，V 型分布时均值更诚实），排除 >2 倍均值的离群值
5. **绝对禁止**：只报一个孤零零的 HRV 数字不说明口径。禁止把单夜中位数当成「你的 HRV 是 XX」

## 数据质量硬门控（v4.9 · 2026-07-29）

### 佩戴检测门控

当 `non_wear_detected=true` 或 `wear_compliance < 0.5` 时，以下解读**必须自动降级**：

| 受影响解读 | 降级方式 |
|-----------|---------|
| 步数、活跃能量 | 标注「⚠️ 设备未佩戴/佩戴不足，活动数据不完整」 |
| 碎步指数、步态 | 标注「⚠️ 设备未佩戴/佩戴不足，步态分析跳过」 |
| 心率-活动耦合 | 标注「⚠️ 设备未佩戴/佩戴不足，耦合分析不可靠」 |
| HRV 解读 | 标注「⚠️ 佩戴不足，HRV 样本可能不具代表性」 |

### 日照 missing 保护

HAE 未导出 `time_in_daylight`（字段缺失）时，`daylight_min` 不应被读作 0。日照×入睡观察触发前必须检查：`daylight_min` 来源字段是否真实存在。缺失 → 不触发日照提醒、不参与比对。

### 活跃能量单位

`health-extract.py` 提取 HAE `active_energy` 时，必须把原始 kJ 除以 4.184 转为整数 kcal，再写入 canonical.jsonl/DB。下游（晨报/skill）禁止自行猜测单位。设备热量是估算值，用户文案写「活动约 N 千卡」，不显示小数，也不把活动能量当作全天总消耗。

### 用户文案与丰富指标选择（v5.2 · 2026-08-08）

- 每天读取完整指标池；按当天解释力选择一个主题和 3–5 个支撑指标。丰富 ≠ 全部堆在主卡，正常且无关指标折叠。
- 首次出现的专业概念必须翻译：CV →「血糖波动 X%（越低越平稳）」；碎步指数 →「活动节奏（走动集中成几段，还是全天走走停停）」；RHR →「静息心率」；HRV 主卡可写「夜间恢复弹性」。缩写/算法只进详情层。
- 主界面禁止：`CV`、`frag_index`、`phys_type`、`evidence_tier`、运动佐证、原因未确认、同窗。内部证据字段与用户文案分离。
- 日历空白只写「没有安排」。只有同一时段心率和步数确实回落，才写「身体活动安静下来」；若心率仍高，写「没有安排，但身体没有明显放松」。
- 红色只用于明确风险，不用来装饰普通静息心率、训练或日程。
- 一组信息一行；步数/千卡/分钟/心率取整。明显异常数值先审计单位和聚合，禁止靠格式化掩盖。
- 建议必须回答「什么时候、做什么、为什么」，优先设计为可验证实验；禁止擅自设置个人健康阈值或承诺结果。
- 卡片标题用具体问题：「昨日轨迹」「这一天身体扛住了吗？」「我们看到了什么关系？」「下一步怎么做？」；不用「身体回应/因果连接/建议卡」。

### 睡眠的时间归属（v5.2 · 2026-08-08）

- 醒来日 HAE 文件中的睡眠，是**这一天开始时的前夜状态**。
- 评价当天训练/会议后的睡眠，必须读取**次日 HAE 文件**。
- 日轨迹固定顺序：前夜睡眠结算 → 当天轨迹 → 当晚收尾 → 次日睡眠结果。
- 禁止把当日凌晨睡眠放到当日晚间日历之后；禁止把训练前的深睡称作训练后的「补偿」。

## 睡眠数据校验（v4.5 · 2026-07-04）

**事故**：某晨报拿了前一天的 HAE 文件（含异地夜睡眠）当成「昨晚（常驻地夜）」分析，整篇报告的睡眠结论全错。

**双重防护**：

### 第一层：提取时校验（health-extract.py v10）
入睡时间是否在预期窗口。分析 7/3→7/4 夜 → 入睡必须在 7/3 18:00 ~ 7/4 12:00。不在窗口 → `sleep_night_mismatch=true`。
用法：`health-extract.py file.json 2026-07-04 --expected-sleep-night 2026-07-03`。不匹配时 exit 2。

### 第二层：报告前检查（health-freshness.py v2）
生成晨报前检查今天的 HAE 文件是否到达。≥09:00 但文件缺失 → `sleep_file_ready=false` → 仅分析白天活动，不编造睡眠数据。

## 五大防护规则

1. 日历深度解读（calendar-insight.py）：负荷画像 + 语义时段 + 可安排空档（面向用户需结合心率/步数，不直接叫恢复）
2. 生理节点×时段（physiology-nodes.py）：分时心率/晨间恢复/连续低活动；日历对应保存在内部证据字段

铁律：
- 行为信号 🆘🍬😴 无法提取 → 数据段显式标注「🚫 Looki 无数据，🆘🍬😴 信号无法提取」，不能沉默跳过

- 生理变化与日历只描述同时发生；用户文案不出现「同窗」等审计词，不写成确诊因果
- 默认模式（无 --no-looki）行为完全不变（回归验证通过）

### hr_activity_coupling 视角（v4.4 新增）

步数 vs 实时心率的 Pearson r：心脏在跟你合作还是在抗拒？
- r > 0.6 → 高耦合，心脏响应灵敏
- r 0.3-0.6 → 正常
- r 0-0.3 → 弱耦合，可能疲劳
- r < 0 → 解耦，需关注。但**力量训练日解耦是正常的**——训练时高心率+低步数会拉低相关性。如果当天有力量训练且用户主观感受良好，解耦可能是训练效应而非恢复赤字。

**校准记录（7/1）**：6/30 上午力量训练 + 全天精力平稳感受好，但 r=−0.43 显示解耦。用户反馈："精力比较平稳，晚上困得早因为醒得早"。结论：力量训练日的负耦合不宜直接解读为"恢复系统罢工"，需结合主观感受和 Looki 场景。

### 格式 1：A+D 信号驱动（行动+数据融合）

## 关键规范

- 禁止用「今天」「今日」描述被分析日，统一用「当天」
- 不强行归因——数据缺位时标注事实
- 生理指标解读限于数据形态标记，不做医学诊断
- 睡眠按醒来日归属——分析 X 日晚睡眠读 X+1 日文件
- **日程分析输出必须量化**：含 `总会议时长 / 最长连续段 / 间隔数`，禁止只有定性描述（如"下午连排"）
