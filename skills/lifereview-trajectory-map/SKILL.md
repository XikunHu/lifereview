# LifeReview 生命轨迹

> 技术 ID：`lifereview-trajectory-map-20260808`（历史安装ID保持兼容）
> 用户名称：**LifeReview 生命轨迹**
> v2.4.0（2026-08-10）：body_signal 成为独立角色而非睡眠 state；首版仅允许稀疏日的显著清醒心率 episode，HRV/低活动暂缓；删除“唤醒水平”和取证话术；只有 body_signal 时轨迹整块隐藏。
> v2.3.0（2026-08-10）：新增安排背景卡与每日最多一张身体独立信号；无锚点时允许判断身体状态与趋势，但禁止猜行为或外部原因；末端洞察证据不足时可省略。
> v2.2.0（2026-08-09）：标题彻底去来源化，删除取证元叙事和强制缺口；按证据等级给出可读确信度，并要求服务端独占可见语义。
> v2.5.0（2026-11-12）：同步最新角色门禁；修复附带脚本与评测的旧约束，支持无节点/无洞察；个人复盘与产品集成分开。

## 输入与适用范围

- 使用有日期、时区、来源、覆盖与可比参照的事实底板；默认先由日报 Skill 的 analysis-contract.md 校验。只有用户提供底板时，不访问额外原始健康资料。
- 普通个人复盘直接输出文字时间轴；服务端独占文案、contract/UI、Metrics隐藏等要求仅用于明确的 LifeBrief 产品集成，不能据此隐藏用户明确索要的身体事实。
- 身体独立信号的“持续显著”必须由输入标明 episode 达标依据、排除睡眠和个人清醒参考；缺少这些依据就不生成 body_signal，不临时发明阈值。
- 不为生成样板默认运行云端脚本。脚本会把输入发送至用户配置的模型服务，需已有明确云端处理授权；优先本会话直接生成。

## 核心目标

让用户一眼看懂：**我做了什么 → 身体哪项数据变了 → 相对我自己的平常水平算高还是低。**

不是罗列指标，不是解释方法论，不是声明"无法确认原因"。

## 六条硬规则

### 1. 四类轨迹角色必须分清

- `已发生行为`：已确认的 Looki 行为、训练或活动记录、步行等设备可核对行为。只有同一时间窗有值得说的身体回应时才做节点。
- `状态边界`：入睡、起床、前夜/次夜睡眠等确定发生的状态转换。
- `安排背景卡`：日历只代表安排，不代表已经执行。若明确安排区间内出现显著且有坐标的身体变化，可以进入同一轨迹，但标题必须带“安排”，正文只能说“这个安排时段……”，不能声明事件执行或行为因果。与睡眠事实冲突时排除；有已确认行为覆盖时由已确认行为拥有身体信号。
- `身体独立信号`：仅在 state/observed/scheduled 最终节点不超过 2 个、且没有任何锚点可以承接时，允许每日最多 **1 张**达标的清醒心率 episode。它使用独立角色 `body_signal`，不复用睡眠/起床的 `state`。标题只写具体观察，如“午间心率高位”，正文只写时间、持续时长、均值、峰值和相对清醒参考；不猜开会、走动、工作、社交、焦虑、咖啡因、饮食、压力、唤醒或其他原因/机制。第一版不生成 HRV 或低活动 body_signal。
- 如果最终只有 body_signal、没有任何 state/observed/scheduled，正式轨迹整块隐藏，身体信息留在 Metrics；这属于合法空轨迹，不回退 legacy。
- candidate 不参与正式配对；candidate-only + 达标身体变化时，candidate 不入轨，身体独立信号可以入轨，但正文不得引用 candidate 标题。
- 有行为但没有身体回应的条目不补位；没有显著增量的信息不生成节点。节点数是门禁结果，不是目标。

### 2. 指标时间窗必须与节点兼容

- 小时指标优先挂到时间窗兼容的已确认行为；没有行为时依次尝试严格重叠的安排背景，仍无 owner 且形成达标 episode 时才做身体独立信号。
- 心率样本必须先排除睡眠区间，再把连续显著样本合并为 episode；单个瞬时 peak 不能独立成节点。第一版不把稀疏 HRV 或低活动片段生成为 body_signal。
- 全天指标只能放在“全天步行/全天活动”等同尺度的真实行为节点或底部洞察，禁止硬挂到 17:00、20:00 等单个事件。
- 只有日期、没有具体时刻的自动识别活动，写 `时段未提供`；不得根据相邻心率、起床时间或日历空档猜测发生时段。
- 同一节点若同时使用多项指标，它们必须共享可解释的聚合窗口；小时值、单点值、全天值不得混称为同一时段回应。

### 3. 解释性数字必须带坐标

用于支持判断的健康/行为指标至少满足一种：

- 个人基线：`HRV 64 ms · 高于 7 天均值 59`
- 当天对比：`步数峰值 2,223 · 其他时段不到 400`
- 跨天位置：`日照 122 分钟 · 一周最多`

日期、时间戳、起止时间和纯结构性时长不需要额外比较，禁止为满足规则制造机械坐标。睡眠总时长、深睡、HRV、静息心率只要展示，就必须有个人基线方向；若事实底板没有个人睡眠基线，睡眠总时长与睡眠结构只能做明确的前后夜对比，不能冒充 7 天基线。

### 4. 标题写行为、安排、状态边界或具体身体观察

- 标题通常 2–8 个汉字：`深度工作`、`社交聚餐`、`QCOM 交流`、`三小时连续日程`。
- 不显示 `Looki：`、`日历线索：`、`日历线索｜`、`日历说明`、`Apple Health：` 等来源前缀；来源只进入内部 evidence 和页面顶部紧凑数据源入口。
- 不把证据层级、取证过程或免责声明写进标题。

### 5. 每句话必须有增量信息

写完自检：删掉这句，用户是否损失信息？不损失就删。解释只保留一句；`interpretation` 与 `relation_copy` 不得同义复述。

### 6. 时长必须写出来

`15:00–18:00 · 3 小时`、`20:00–22:00 · 2 小时`。不许只说"最长的连续安排"。

## 永久禁用表达

写了等于没写，一律禁止：

- 没有构成已识别的高点
- 为当时状态提供了参照
- 只能确认同时发生，暂不判断原因
- 现有证据不能确认原因
- 附近记录只能提供背景
- 覆盖了当天多个关键时段
- 身体信号在不止一个时段出现
- 恢复要结合两项一起看
- 深睡与 REM 都有记录
- 这是日历计划线索
- 没有足够记录可核对
- 不据此认定实际出席
- 没有 Looki 或训练证据
- 不补写行为
- 日历空白不代表休息
- 这是一条待核对线索

**标题来源前缀（永久）**：`Looki：`、`日历线索：`、`日历线索｜`、`日历说明`、`Apple Health：`。

**术语（永久）**：

- Nixon 禁用的 HRV 旧别名全线废止，一律写 `HRV`；不做首次括注，不做后续简称。
- `CV` → `血糖波动 4%（越低越平稳）`
- `RHR` → `静息心率`
- `REM` → `快速眼动睡眠`
- 不显示：frag_index、phys_type、evidence_tier、运动佐证、原因未确认、同窗

## 分级确信与因果边界

不要向用户声明取证方法；根据行为证据和指标时间窗，选择最有信息量且不过界的语气：

| 证据 | 允许语气 | 好例 |
|---|---|---|
| 训练/运动记录 + 同窗心率 | 可直接写身体响应 | `力量训练把心率推到 142 bpm，为当天最高。` |
| confirmed 社交/工作 + 同窗升高 | 描述行为期间的变化，不补未记录动作 | `社交期间心率均值 72 bpm，比其他清醒时段高 10。` |
| 只有日历事件 + 同窗变化 | 只陈述安排时段共现 | `安排 · 房东来；这个安排时段心率均值 92 bpm，比当天均值高 21。` |
| 无行为/安排 + 稀疏日达标清醒 HR episode | 只描述可核对身体数据 | `午间心率高位；11:40–12:35 均值 86 bpm、峰值 91，比清醒时段均值高 16 bpm。` |
| 无行为/安排 + 单点或普通波动 | 不做节点 | 删除或留在指标全貌 |
| 活动多但心率平 | 直接写反差 | `活动不少，心率没跟着上去。` |

坏例（不要输出）：

- `训练记录与心率高点落在同一时段。`（只复述共现，过度保守）
- `日历只说明连续三小时计划，不据此认定实际出席。`（向用户展示取证过程）
- `密集日程导致 HRV 下降。`（把时间相关写成确定因果）
- `心率高于极限。`（没有个体阈值）

其余边界不变：低步数只代表少移动；无进餐记录不命名餐后反应；单点 HRV 高值写“单次高值”；没有行为证据时不靠心率反向编造行为。

## 维度多样性配额

同一指标族在轨迹节点主体内**最多出现 2 次**；第二次必须形成峰值、回落或前后对照。底部洞察可以跨族引用，但不能复述节点原句。心率不得因覆盖率高而成为默认指标。

| 族 | 字段 | 何时值得写 |
|---|---|---|
| 睡眠结构 | 总时长/深睡/快速眼动/入睡起床 | 有可靠记录与参照时 |
| 恢复 | HRV、静息心率、夜间心率 | 有可靠记录，必带基线 |
| 心率负荷 | 逐时均值/峰值、运动心率 | 有行为对应时 |
| 活动结构 | 步数、峰值步数、集中度、活动能量、锻炼分钟 | 有峰值或结构变化 |
| 步态质量 | 步速、步长、不对称、双支撑 | 超出个人常态才写 |
| 环境暴露 | 日照分钟、环境声 | 明显偏离才写 |
| 代谢 | 血糖均值/范围/波动 | 有餐时或明显波动 |
| 呼吸循环 | 呼吸率、血氧 | 明显偏离才写 |

生成前先问：今天哪 3–4 个族真的动了？只写动了的。

## 节点语义格式

```text
时间：09:00–10:00
行为：力量训练
指标：心率 100–142 bpm；步数 1,414
解释：力量训练把心率推到 142 bpm，为当天最高。
```

- UI 可按当前产品契约使用左行为/右身体双轨，Accessibility 可自然堆叠；Skill 不规定与产品冲突的固定布局。
- 行为标题、指标（最多 2 项，确有必要才 3 项）和一句解释必须可独立渲染。
- 数据源、`evidence_tier`、内部 relation enum 和免责声明不进入可见字段。

## 两句洞察

固定最多两句，来自**不同族**。只有确有两条真实、可追溯到最终节点的跨维度洞察时才显示；不足时整体省略，不复制、不补模板。前夜睡眠与次夜睡眠仍属于同一睡眠族，不能分别占两句。每句必须含：具体数字 + 方向词（高于/低于/最多/最少/唯一）+ 跨时段或跨指标关系；不得复述节点正文。身体独立信号可以进入洞察，但只能描述身体趋势，不补行为或原因。

自检：这句话换到任何一天还成立吗？成立就是废话。

好例子：

```text
两个洞察
1. 日照 122 分钟是过去一周的四倍以上，步态不对称降到 0.2%，这是最近走得最舒展的一天。
2. 睡了 7.5 小时、HRV 回到 64，静息心率却是一周最高的 55；恢复和心脏负荷这次没有同向。
```

坏例子：

- 今天整体状态不错。（无数据）
- HRV 下降说明压力大。（单日过度因果）
- 建议早睡多运动。（不是洞察）
- 行为与身体读数覆盖了多个时段。（换哪天都成立）

## 视角池

生成多版时，每版换一个真问题：

1. 基线偏离：今天哪几项脱离了我的均值
2. 结论优先：主矛盾是什么
3. 矛盾信号：恢复变好但另一项变差
4. 活动结构：总步数由什么组成、峰值在哪
5. 环境暴露：日照/声音是否解释了这一天
6. 步态质量：走路本身有没有变化
7. 代谢曲线：血糖变化落在哪个行为时段
8. 日程密度：事情最多时身体是否最紧
9. 训练余波：训练后多久回落
10. 起点与结果：前夜底子与次日睡眠
11. 低活动对比：不动是否等于休息
12. 睡眠结构：总量内部如何分配

无信号的视角不用：步态只有超出个人常态才讲；单次正念不独立成视角；正常血氧不为丰富度硬塞。

## 睡眠归属

D 日文件中的睡眠是开始 D 日时的底子；评价 D 日行为之后的睡眠必须读 D+1。

## 可选批量脚本

- 日常只生成信号最强的1版；用户要求多版时按不同问题各生成1版，不设节点下限。证据不足时允许没有轨迹或省略末端洞察。
- 推荐 `scripts/run_deepseek_resumable.py --input facts.json --outdir output --model MODEL --api-root BASE_URL`；名称保留用于兼容，但模型不固定，必须支持 Anthropic Messages 协议。模型选择由当前服务可用目录与用户要求决定。
- 默认1版，`--variants 10`才生成10个视角；并发最多3。通过环境变量PROMA_API_KEY/LLM_API_KEY提供密钥，不写入文件或命令行。
- 输入、Skill、runner、模型、服务地址和生成参数共同决定续跑标识；改变这些条件不能混用旧结果。空正文或截断算失败，部分失败以非零状态退出。
- 原 `run_deepseek.py` / `run_deepseek_batch.py` 为兼容入口，转用同一套规则；`--output`可指定合并文件。脚本不发送飞书、不写健康数据库。
